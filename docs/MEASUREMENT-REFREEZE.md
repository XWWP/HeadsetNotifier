# 实测：解冻后多久会被重新冻结（2026-11-05）

对应 `docs/POWER-REVIEW.md` §7.1，这份数据是该评审里「2 秒频率要不要改」的唯一实测依据。
原始采样：`docs/measurements/refreeze-2026-11-05.log`（每行一次采样，逐行可查）。

## 测试条件

| 项 | 值 |
| --- | --- |
| 设备 | 一加 / ColorOS（Android 15） |
| 应用版本 | 2.7.5（versionCode 22） |
| 应用状态 | 后台 + **前台服务在运行** + 已连接蓝牙耳机（SCO 与 A2DP 同时在线） |
| 屏幕 | 熄灭 |
| 守护脚本 | **已暂停**（否则每 2 秒解冻一次，测不到系统的真实行为） |
| 采样 | 每 5 秒一次，目标 120 次；实际 86 次（见下面第 3 条） |
| 时段 | 21:12:13 → 21:23 左右 |

## 结果

```
样本总数            86
freeze=1（冻结）     2
freeze=0（解冻）    83
```

状态切换点只有两处：

```
21:12:18 冻结   → 21:12:23 解冻（≤5 秒）
21:14:18 冻结   → 21:14:23 解冻（≤5 秒）
```

**96.5% 的采样时间里应用处于解冻状态**；11 分钟里只被冻了两次，且每次都在 5 秒内自行解除（这期间守护脚本是停着的，所以解除是系统自己做的，不是脚本的功劳）。

## 结论

1. **有前台服务 + 耳机连接时，ColorOS 基本不冻这个应用。** 11 分钟只出现 2 次、累计不到 10 秒的冻结。评审里「即使有 FGS 也会被冻」在这台机器上只占很小一部分时间。
2. **就算被冻，也不是"冻住不放"。** 两次冻结都在一个采样周期（≤5 秒）内解除——说明重冻结不是持续压制，而是偶发评估后很快放开。
3. **息屏时 `sleep` 没有 5 秒精度。** 86 个样本覆盖约 11 分钟，平均间隔约 7.7 秒，而设定是 5 秒——设备确实进了 suspend，把 `sleep` 一并推迟了。这直接印证评审 §1.3 的推断：**「每 2 秒解冻一次」在息屏场景下本来就不成立**，付出的是唤醒成本，拿到的是被拉长且抖动的实际间隔。

## 对策略的影响

- 「2 秒」在这个场景下收益极低：11 分钟里脚本若在跑，会做约 330 次解冻检查，其中只有 2 次真的写到 `cgroup.freeze`，其余全是空转唤醒。
- 建议把 `high` 模式间隔放宽到 **5 秒**（最坏播报延迟 5 秒，可接受），并把「一观察到 `freeze=1` 就临时收紧」保留为可选优化。
- 这与评审 §3 的方向一致：按「是否真的发生冻结」调整，而不是按时间猜。

## 这份数据的局限（不要过度解读）

1. **只覆盖了「有前台服务」的状态。** 没测「无前台服务、只有监听服务」被冻的情形——那种状态下 ColorOS 可能冻得更狠，2 秒也许仍有意义。要补测可以把 `KeepAliveService` 停掉再跑一遍同样的采样。
2. **脚本是停着的。** 真实运行时脚本每 2 秒解冻一次，系统可能因此更少进入冻结状态，也可能相反——这一点无法在停脚本的前提下观测。
3. **样本只有 86 个、11 分钟。** 不足以覆盖「长时间无事件」或「刚播报完」这类窗口。
4. 两次冻结都发生在整两分钟间隔上（21:12:18 / 21:14:18），像是周期性评估；样本太短，不能断言周期。
