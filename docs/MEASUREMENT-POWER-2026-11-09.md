# 耗电实测（2.7.9 第一半上线后）

## 采集条件

- 设备：一加 / ColorOS，电池容量 5920 mAh
- 统计窗口：`Statistics since last charge`，起始 2026-11-08 18:05:05
  → 采集于 2026-11-09 15:45，约 **21 小时 40 分**
- 窗口完全落在 2.7.9（versionCode 26，2026-11-08 11:59 安装）之后，
  没有混入旧版本数据
- 期间蓝牙耳机（18:5C:A1:52:36:BC）连过，TTS 实际播报 3 分 02 秒

## 结果（`dumpsys batterystats`，UID u0a645）

| 项目 | 数值 |
|---|---|
| 该 UID 估算耗电 | **5.03 mAh** |
| ├ CPU | 2.04 mAh |
| ├ 音频（TTS 播报） | 2.75 mAh（3m02s） |
| ├ 屏幕 | 0.236 mAh |
| └ wakelock | 0.0002 mAh（86 ms） |
| 前台服务计时 | 20h44m |
| 设备总耗电（同窗口） | 3646 mAh |

占比：5.03 / 3646 = **0.14%**；折算成电池百分比约 **0.085%/21.7h ≈ 0.09%/天**。

现网 CPU 采样（耳机连着、30 秒轮询在跑）：
`/proc/<pid>/stat` 的 utime+stime 在两分钟内涨了 25 tick（0.25 s），
约等于单核 0.2% —— 一天约 3 分钟 CPU 时间。

## 结论

1. **第二半不做。** 闸门是"提升不到 1–2% 就不做"，实测这个 App 整体只占 0.14%，
   停掉轮询的理论上限也就 1 mAh 量级（≈0.02%/天），低于 batterystats 的可信分辨率。
   再花力气把 tick 换成系统闹钟，收益看不见，风险（冻结不可解、粒度退化到 9–15 分钟、
   失败无日志）却是实打实的。
2. **"耗电"从来不是这个 App 的问题。** 真正的痛点是"又不播报了"，即监听绑定与
   进程存活，那属于 P0-1 的范畴，跟轮询频率无关。
3. 第一半保留：代码更简单（不跑就是最好的省电）+ 状态页可自证停摆，
   即使耗电上看不出差别也值得留。

## 顺带发现（已在 2.7.10 处理）

`com.github.metacubex.clash.meta` 每秒发一次通知更新，导致 `onNotificationPosted`
每秒被调用一次，日志里 99% 是 `skip allowlist: ...` 这一行，
粗算 8.6 万行/天。它比 30 秒轮询的唤醒次数高 30 倍，是当前最大的唤醒源
（代价仍小，属于噪声级别）。

2.7.10 起 `logSkip()` 按「原因 + 包名」做 60 秒节流，与 `recordSkip()` 的节流对齐。
实测：同一条通知每秒刷新，日志从每秒 1 行降到每分钟 1 行；
副作用是 logcat 环形缓冲不会再被同一行刷满，故障现场能留住了。

注意：节流解决的只是"日志和内存记录"，回调本身仍然每秒进来一次 ——
这是系统行为，应用无法按包名退订 `onNotificationPosted`。
