# 冻结复现与解冻路径验证（2026-11-06）

## 为什么做这个

四组间隔实测（见 `MEASUREMENT-INTERVAL.md`）里 `frozen=1` 出现 0 次，导致两个问题一直悬着：

1. 「5 秒够不够快」没有分母，答不上来；
2. 模块里 `freeze_file_of()` / `thaw()` 这段解冻代码在真机上累计解冻 0 次——**从未被执行过**，属于未验证代码。

## 设备实际 cgroup 布局

```
$ cat /proc/<pid>/cgroup
4:freezer:/
3:cpuset:/background
2:cpu:/background
1:blkio:/background
0::/apps/uid_10645/pid_31261
```

- cgroup v2 冻结文件：`/sys/fs/cgroup/apps/uid_<uid>/pid_<pid>/cgroup.freeze`（存在，可写，0=运行 1=冻结）
- 同时存在 cgroup v1 freezer 挂载 `/dev/freezer`（`frozen/`、`thaw/`），为 ColorOS 遗留通道
- 模块 `freeze_file_of()` 按 `/proc/<pid>/cgroup` 的 `0::` 行推算，实测路径正确（日志已验证）

## 系统冻结为什么复现不出来

进程在**前台服务**状态时 `oom_score_adj=430`，系统不会把它当 cached，也不会冻结它：

```
$ am freeze 31261
Freezing process com.sakura.airannounce (31261) sticky=false
$ cat /sys/fs/cgroup/apps/uid_10645/pid_31261/cgroup.freeze
0        # 仍是 0，冻结未生效
```

即：只要应用有前台服务（本项目的 `KeepAliveService` / 通知监听绑定），冻结就不会发生。
之前四组实测全部 `frozen=1` 为 0 是**正常现象，不是测试失败**。

## 受控复现：直接写 cgroup.freeze

绕过 AMS 判断，直接写内核接口，等价于冻结本体：

```
echo 1 > /sys/fs/cgroup/apps/uid_10645/pid_31261/cgroup.freeze
```

写入立即生效；模块在下一个 5 秒 tick 读到 `1` → 写 `0` → 解冻成功。

结果（10 次连续采样，模块处于 high 模式 5 秒一轮）：

| 次数 | 从冻结到被解冻 |
|---|---|
| 1 | 1050 ms |
| 2–10 | 3900 / 3900 / 3900 / 3900 / 3900 / 4050 / 4050 / 3900 / 4050 ms |

- 最坏接近 5 秒，多数落在 3.9–4.05 秒（与 5 秒 tick 相位对齐）
- 日志确认：`解冻 pid=31261（累计 3 次）`、`（累计 8 次）` —— **thaw 路径首次在真机上真实执行并成功**
- 同时确认 `THAW_COUNT` 只在读到 `1` 时自增，不写 0 不计数，逻辑正确

## 结论

| 项目 | 状态 |
|---|---|
| 冻结文件路径推算 | 真机验证正确 |
| `thaw()` 写 0 解冻 | 真机验证成功（此前从未执行） |
| 解冻延迟 | 0–5 秒，受 5 秒 tick 决定，实测最坏 ~4 秒 |
| 系统自然冻结 | **仍未复现**（进程带前台服务，不可冻） |
| 真实失效模式 | 进程被直接杀死（09:58 日志 `应用进程已不在`），不是冻结 |

## 局限

1. 本实验是**受控注入**冻结，不代表性系统自然冻结的触发频率和持续时长；
2. 真实自然冻结需要进程进入 cached（即前台服务消失），而前台服务消失后进程往往直接被杀，两者难以分离；
3. 冻结期间蓝牙连接回调是否丢失，仍需真耳机 + 冻结同时发生才能验证。

## 下一步

1. 在耳机连接瞬间人工注入冻结，验证「连接事件是否丢失」——这决定 5 秒是否必须缩回 2 秒；
2. 若连接事件会丢，high 模式应回调到 2 秒，代价用实测唤醒次数换算；
3. 若不会丢（系统会补发回调），维持 5 秒，并把本条写进功耗说明。
